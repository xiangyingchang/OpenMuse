# 核心文件与长期记忆方案 v0.2

日期：2026-10-10。这是实现基线方案；D31 已授权实现，但其中详细 schema/同步默认值不是用户逐项批准的产品选择。目标：用户读得懂、改得动；模型可替换；数据可迁移；长期迭代不丢来源与历史。当前实现差距见[需求覆盖审计](REQUIREMENT_AUDIT_2026-10-10.md)。

## 设计原则与事实边界

用户提供的 Muse SOUL.md 展示了人格可演化、修改后告知、用户可编辑的机制；界面“About this file”不属于正文。官方公开资料确认记忆可查看编辑，但没有公开完整记忆算法。社区快照与 nanoMuse 证据见 [研究说明](MUSE_MEMORY_RESEARCH.md)。以下字段、目录、事务和同步协议是 OpenMuse 的建议，不冒充 Muse 原实现。

推荐采用“结构化记录 + 可编辑 Markdown 文件 + 可重建检索索引”。文件不是装饰性导出，也不是让各模型任意改写的第二套数据库。每个对象只设一个写入入口，文件编辑和聊天修改都进入同一变更流程。

## 每个核心文件做什么

| 文件 | 内容与角色 | 读取和迭代 |
|---|---|---|
| SOUL.md | 陪伴者价值、语气、习惯、协作方式；从模板开始 | 每轮读取紧凑正文；允许逐渐演化，留下差异和原因，修改后告诉用户；用户可编辑和撤销 |
| IDENTITY.md | 名字、头像引用、称呼与身份版本 | 初次加载、身份变化时更新；不与 SOUL 重复维护名字 |
| USER.md | 当前用户画像的精简视图，优先显示身份、地点、工作、偏好、习惯等资料 | 每轮读取当前有效且属于画像类别的记录；条目引用同一 claim ID，编辑自动维护条目会更新结构化记录 |
| GLOBAL.md | 按主题组织的导航索引，链接到 MEMORY.md 的完整条目 | 每轮读取短索引；索引由结构化记录生成，链接不构成另一份事实；自动索引区外允许手写背景 |
| HEARTBEAT.md | 主动工作的意图、启用状态、时区、频率、设备和最近结果 | 调度检查时读取；编辑形成结构化计划变更；正文自身不能唤醒 iPhone |
| AGENTS.md | 工作区约定、工具使用提示和上下文路由 | 启动与相应任务时读取；不可替代宿主权限校验 |
| MEMORY.md | 当前有效的长期记忆账本，显示类别、来源性质、日期、范围和推断状态 | 读取完整当前视图；编辑自动维护条目会更新同一 claim；旧版本与来源证据留在结构化修订/来源记录 |
| memory/daily/ | 按日期整理的新信息与经历 | 相关时读取，合并重复条目；必要历史保留，不无限常驻上下文 |

全部必需文件首次创建并可查看。空文件使用短模板，不编造画像。文件说明和编辑控件属于 UI 元数据，导出正文不夹带“About this file”。凭证放 Keychain；真正的权限与授权由宿主独立校验，SOUL 自我修改不能获得额外权限。2026-10-10用户已确认：人格可自行成长，每次修改告知；核心目的与权限边界由用户决定（D21）。

## 本地存储与便携目录

每台设备持有本地事务数据库及工作区。本地 SQLite 保存文档、事实、来源、目标、计划、修订和待同步记录；不是两台设备共同打开的 iCloud 文件。结构化记录是运行时状态来源，Markdown 是该状态可编辑的工作区表面。原始导入独立保存；向量与全文索引可重建。

便携导出结构建议：

```text
OpenMuse-export/
  manifest.json
  SOUL.md  IDENTITY.md  USER.md  GLOBAL.md
  HEARTBEAT.md  AGENTS.md  MEMORY.md
  records/       # documents, claims, sources, goals, schedules: JSONL
  changes/       # revisions 与脱敏变更事件: JSONL
  conversations/ # 开放格式会话与来源引用
  memory/daily/
  artifacts/     # 行程等成果与版本
  attachments/   # 文件正文与内容校验值，按附件记录引用
```

维护运行、反思、原话证据和候选建议都作为结构化记录导出；第一期不新增 `DREAMS.md` 或 `dreams/` 作为第二份真值。身份页目前只展示最近三次回顾；更早记录仍在结构化运行数据中，可随同步和包含聊天的完整迁移包携带，但 App 尚无完整历史浏览入口。若以后需要日记式阅读或分享，应先从记录生成只读/可重建视图，不允许它与数据库分别编辑。`memory/daily/` 是未来经历笔记的预留目录，当前近期回顾不会生成日记文件。

这份目录是完整迁移包；日常工作区可按需物化，不要求每次对话全量导出。数据库提交后保留待同步/导出变更，确认持久保存前不得丢弃。仅索引可任意重建，不能把尚未导出的数据库误当可丢缓存。

## 结构化记录

所有对象带稳定 ID、schemaVersion、revision、来源、创建与修改时间、设备及版本关系。事实另外带主体、范围、类型、证据引用、可信状态、有效期和替代关系。目标、计划、调度、内容反馈单独建表，不能只存在 Markdown 自由段落里。目标进展事件以不可变记录保存 goalId、sourceMessageId、action、stepId 和时间；稳定 ID 让同一来源重复处理保持幂等，事件进入现有设备同步和迁移协议。

实现补充：`SourceRecord` 与 `ImportRecord` 已作为独立结构化记录类型写入 SQLite records/revisions/outbox，连接器资料、AI 记忆快照和 ChatGPT 历史导入会引用它们。底层仍是带 kind 的通用记录表，不是独立关系表；未覆盖关系的外键也不由 SQLite 强制，因此来源完整性还需迁移预检和清理测试。

```json
{
  "schemaVersion": 1,
  "id": "claim_demo_01",
  "revision": 1,
  "subjectId": "user_demo",
  "kind": "constraint",
  "text": "本次旅行避免清晨出发",
  "scope": {"type": "goal", "id": "trip_demo"},
  "status": "active",
  "confidenceType": "user_explicit",
  "sourceIds": ["message_demo_04"],
  "validFrom": null,
  "validUntil": null,
  "supersedesId": null
}
```

这是虚构示例。“这次别早起”只服务于这次旅行；重复观察可以形成候选偏好，不能偷偷改成“用户永远讨厌早起”。引用朋友的愿望须绑定朋友主体，不能当成用户目标。

记忆 claim 的 `validFrom` 与 `validUntil` 是可选的有效时间边界；空值表示目前没有可靠边界，不代表模型可以自行补日期。明确事实以原消息时间作为 `validFrom`。明确纠正同一偏好时，旧 claim 保留来源并在纠正时间结束有效期，新 claim 从同一时间开始；导入的其他 AI 历史快照不推测生效或失效时间。用户可在记忆页调整日期，截止日期按用户本地日历日含当天保存。查询只注入 `active` 且在有效时间范围内的 claim；过期/未来记录也会从 USER.md 自动投影中过滤，避免绕过结构化检索。该路径目前只覆盖明确偏好纠正，不解决一般事实冲突、主体辨析或从自然语言推断时间。

文档记录保存原文、类型、版本和用户编辑区。USER/GLOBAL 的摘要块引用事实 ID，HEARTBEAT 引用 scheduleId；同一信息多处出现仍只有一个来源。原始证据与归纳分开，推断与明确陈述分开。

## 如何读取

1. 启动检查 schema 与迁移状态，取一个一致版本快照，加载身份和人格。
2. 每轮读取当前 SOUL、精简 USER、GLOBAL 摘要与适用工作区约定；给不同材料标明角色和来源。
3. 根据当前话题检索有效事实、相关原始片段、目标及成果；只补充相关日记，不无界拼接全部文件。
4. 调度回合额外加载对应 HEARTBEAT 条目、预算、运行状态与暂停信息；普通聊天不需要塞入全部计划。
5. 以明确上下文预算优先保留用户当前请求、纠正、必要事实和任务状态；过长内容分块检索，不静默截掉重要边界。
6. 会话或工具边界检查新修订。普通变化在下一回合生效；撤销权限、暂停和遗忘由宿主立即检查，不能等模型读文件。

导入邮件、网页和其他 AI 的画像作为资料，不作为可提升权限的指令。模型切换重建相同语义上下文，不需要改人格、事实或目标。嵌入模型变化重建索引，记录模型与维度，保留原数据。

## 如何更新和编辑

聊天 → 提取候选 → 核验主体/范围/来源 → 生成变更 → 校验 → 本地事务提交记录、修订、待同步事件 → 原子更新文件视图 → 下一回合读取。

明确新信息和用户纠正可更新当前状态；短期状态设复核时机；不确定推断保留候选，不硬写成事实。冲突处理看范围和来源，不能把“最新消息”机械地当成所有旧事实的反证。

SOUL 更新走文档差异流程，记录修改内容与理由，告诉用户并支持撤销。不能通过总结抹去用户明确指定的人格；外部材料不能自行改 SOUL。权限规则与人格内容分离，但不把人格退化成固定不变的品牌提示词。

当前实现切片：只从用户直接反馈“太严肃/太正式”“回复太长/太啰嗦”“问太多”这三类风格信号映射到固定协作习惯；不接受问句、第三方描述或权限/安全要求作为人格修订。SOUL 文档与来源消息、原因、目标修订号在 SQLite 同一事务保存并同步；本轮成功或失败时都向用户说明，身份页展示原句且可撤销。撤销只移除对应的 OpenMuse 管理习惯行，保留其他自动/手动内容；若该行被手动改写，拒绝自动撤销并提示用户查看。此有限规则闭环不等于通用人格反思或模型自行决定改变 SOUL。

附件以不透明 ID 保存为工作区本机独立文件，SQLite `AttachmentRecord` 保存来源消息、媒体类型、字节数和 SHA-256；消息只引用稳定附件 ID。读取时核验长度和摘要。TXT/Markdown/PDF 正文可在每轮最多 20 KB 的预算内进入模型上下文，并明确标记为不可信资料。已配对 iPhone 发起同步时，Mac 桥接通道只接受数据库中已登记的附件 ID，按原始二进制传输并验证长度/摘要；同 ID 摘要冲突拒绝覆盖。包含聊天的 JSON 迁移包携带附件元数据和原件，不含聊天的包会列出省略项并清除引用。彻底删除附件会写删除墓碑、移除当前消息引用、删除本机原件并在其他设备收到同步后清理副本；导出时过滤历史修订中的旧附件 ID。图像/音频/视频、完整历史原件清理、受控备份清除仍未实现。

App 文件编辑器携带 baseRevision。模型也只能提交带版本的补丁。用户用外部编辑器改文件时，导入完整原文并检查基线：可识别块转为补丁，自由正文保留为用户笔记；模糊改动形成待确认草稿。解析失败保留原文与错误，不覆盖、不偷偷生效。运行中的 DB、文件投影和同步快照不允许各自无条件覆盖对方。

崩溃恢复重放已提交修订、重建投影；失败候选不变成成功记忆。撤销是新修订，旧版本保留用于解释，彻底遗忘另走删除流程。

## 主动维护与 HEARTBEAT

Dreaming 按“经历整理 → 主题反思 → 长期记忆确认/晋升”理解，与人类记忆巩固只有功能类比，不声称模型具有人类睡眠或主观体验。OpenClaw 官方文档当前描述 Light、REM、Deep 三阶段：前两阶段整理和反思候选，Deep 才能更新精选的 `MEMORY.md`；`DREAMS.md` 是人类可读的回顾日记，不是长期记忆晋升来源。OpenMuse 借鉴“经历、反思、持久记忆”分层，不复制其后台调度、门槛和文件写入算法。

2026-10-12实现切片：原始聊天继续作为带来源的经历记录；`MaintenanceRunRecord` 保存本次回顾的模型状态、Token使用、摘要、协作反思和逐字原话证据；它是按运行归档的审计记录，不是用户画像，也不注入普通模型上下文。`MaintenanceProposalRecord` 保存事实、理解、协作习惯、目标小步骤和一对一记忆更新候选；逐条确认后才进入结构化记忆、SOUL 或目标事务。明确的非敏感用户陈述继续按既有规则即时入库，Dreaming 不替代这条路径。用户忘记某条记忆时，会一并删除引用相同来源的维护运行与建议及相关修订；不含聊天的迁移包省略这些私密记录，含聊天的迁移/同步携带结构化运行记录，不生成第二份日记文件。

边界：反思本身不能让 Agent “学会”或证明理解有所改善。持续了解用户依靠有来源的 `MemoryClaimRecord`、用户确认后的人格协作习惯修订、目标进展和后续召回效果；当前还缺跨周主题强化、稳定偏好自动修订和“相似场景中是否真的做得更好”的结果验证。

回顾仍是一轮受限模型请求，逻辑上覆盖经历整理、反思与候选晋升，不是三个独立运行阶段；范围为近七天、最多24条原创消息和有限匹配记忆/目标。反思需有逐字用户原话证据并经过敏感内容过滤，只供用户查看。引文能核对出处，不能证明模型归纳的语义正确，推断与外部资料仍须用户确认。每日自动回顾默认关闭；iOS 只请求机会式 `BGAppRefreshTask`，不能承诺锁屏准时执行或强制退出后唤醒。尚无跨周强化分值、稳定事实的通用语义抽取/冲突发现、后续相似情境的行为效果验证、完整目标研究或关系维护、货币硬预算、跨设备原子预算与完整漏跑队列。

计划记录至少包含 enabled、timezone、cadence、nextDue、ownerDeviceId、missedRunPolicy、预算、关联目标、lastAttempt 与 lastSuccess。HEARTBEAT 呈现这些记录。用户写“最近别提醒旅行”生成暂停补丁；写模糊意图先澄清，不能直接编译为未知 cron。

iCloud 不负责执行或锁定任务。离线手机只能在系统实际允许的时间工作；任务过期可按策略补跑、跳过或等待用户。界面区分计划时间、实际运行、检查结果和是否通知。维持人格和记忆的后台工作也受同样限制。

## iCloud 与冲突

同步稳定记录与版本事件，CloudKit 私有库为候选；附件/便携文件可用 iCloud Drive。路线尚待技术验证。不同设备通过同一协议修改对象；并发冲突保留双方和共同基线，不只用设备时间作最后写入覆盖。

用户暂停和遗忘优先于后台自动更新；重新启用必须有明确操作。SOUL 并发改动不能让两个设备默默形成两个人格。自动摘要可重建，用户自由文本冲突必须保留并可选择合并。

同一周期任务指定设备，交接状态可见。iCloud 最终一致时无法承诺全局只执行一次；支付、发信等外部动作不因记忆同步获得自动接管授权。

## 导出、迁移与遗忘

manifest 包含协议版本、最低读取版本、导出 ID、生成端、组件清单与校验值。开放 JSON/JSONL + UTF-8 Markdown 保留记录与来源关系，附件单独校验。导出默认不含凭证；用户可选择会话/附件范围，缺省项明确列出。

导入先预检版本、校验、稳定 ID 和引用，再展示变更；备份后在暂存区迁移并一次提交。重复导入不重复建目标。保留未知扩展字段；高于支持版本时只读或拒绝写入，不能猜着覆盖。迁移不自动恢复旧任务的运行授权。每次协议升级有迁移函数、备份与失败回滚路径，不能仅靠模型改写文件。

“忘记”覆盖事实、摘要、索引、日记、反思、源文本相关片段和任务衍生信息；保留不含原文的删除标记，防止同步/旧材料自动恢复。来源抑制策略和备份保留周期需向用户说明。离线设备未确认删除时显示待传播，不能声称所有副本已清除。不可同时承诺无限不可变原文历史与彻底遗忘；彻底删除时清理含原文修订和受控备份。已经发给模型供应商的数据不能靠本地删除撤回。

## 必须通过的验收

- USER 修改后对话、GLOBAL 引用与检索一致；并发修改不丢原文。
- 一次旅行约束不升级为长期偏好；纠正和到期状态真实生效。
- SOUL 可演化、告知、撤销；编辑不改变宿主访问权限。
- HEARTBEAT 暂停立即阻止下一步；漏跑有状态，不伪装成功。
- 断电/崩溃后修订和文件投影一致；解析失败保留用户文本。
- 换模型、换嵌入模型、导出到新设备仍有身份、来源、目标与成果。
- 旧版本迁移、重复导入、同步乱序、离线遗忘和恢复旧备份都有明确结果。

最早技术关卡的记录—文件—读取—纠正—迁移闭环已有部分实现：核心 Markdown 文件和结构化记忆可往返，USER.md 手工修改会成为带来源的新修订；当前工作区导出为 ZIP 容器，内含 manifest、records/revisions/conflicts JSONL 与独立附件原件，带校验、聊天范围、重复包保护和冲突保留，并继续兼容读取早期 JSON 包。它不是上述完整 Markdown 目录布局；通用 JSON 记录的未知字段保留、崩溃注入、外部备份清理和完整遗忘范围仍未通过。

## 重点研究补充（2026-10-10）

## 2026-10-11 现居地搬迁更新

直接写“我住在杭州”“我最近从上海搬到杭州了”等当前居住陈述时，新 claim 会作为用户明确事实保存。若旧 claim 也表达现居地，则旧记录保留来源与修订、状态改为 `superseded`，并在新消息时间结束有效期；USER.md 当前投影只显示新现居地。“我来自上海”属于籍贯/来源地，与“我搬到杭州”属于现居地，两者同时保留。同一句同时陈述籍贯和当前居住地时，以明确的当前居住子句更新现居记录，并保留独立的籍贯 claim。只有搬迁计划或不确定搬迁、且没有当前居住子句时，不把含搬迁的整句记成长期事实。问句、第三方陈述和假设不触发自动记录。这是一个窄范围的当前状态更新，不代表已经解决一般事实冲突或主体/时间抽取。

一次模型请求统一计算人格、核心文件、召回记忆、侧聊摘录、近期消息、附件正文和当前请求，并预留输出额度。输入长度由本地通用估算，不等同任一供应商的精确 tokenizer；构件内容、工具过程输出和各供应商的隐藏包装尚未全部纳入同一成本估算，后续需继续验证。

## 2026-10-10 记忆彻底遗忘切片

记忆页提供与“撤销并保留历史”分开的“彻底忘记”。本地事务创建只保留记录类型/稳定 ID/时间的墓碑，删除当前记忆、全部修订和相关冲突；既有同步事件以空载荷 schema v2 保留设备序号，避免后续事件序号断裂。配对设备收到墓碑后删除对应资料和本机历史；迟到的旧写入会被墓碑拦截。当前 USER.md 投影会删除，相关修订和旧投影同步事件会清理，再保留最新已清理的文件快照继续同步。工作区导入会跳过墓碑对应的旧记录和早于遗忘时间的 USER.md 快照。

这不是全盘擦除：用户主动选择“彻底忘记”后，来源聊天仍保留；离线设备在重新同步前仍有副本，用户另存到 OpenMuse 管理范围外的文件也不会被删除。旧版客户端不理解 schema v2 脱敏事件或 `deletion-tombstone` 类型，必须升级后同步。旧档案独立导入到一个没有新墓碑的新设备，仍可能恢复内容。真实跨设备、离线和升级过程尚未在 iPhone 真机验收。

## 本轮协议细化：v1实现基线（2026-10-10）

补RUNTIME_PROTOCOL的事件信封；本地对象表至少有documents/documentRevisions、claims/claimRevisions、sources/imports、messages/conversations、goals/steps/progressEvents、schedules/maintenanceRuns、artifacts/revisions、attachments、outbox/deviceCursors、deletionMarkers。主键稳定UUID，修订不可变并带parent IDs，外键不允许来源静默丢失；索引不承载唯一事实。事务内写修订+当前指针+outbox；文件更新失败标待投影，读取同一提交的DB视图，重试原子投影。

结构化文件块用稳定claimId/doc blockId关联；自由段落保存在document block，不能用正则强行解释成用户事实。SOUL与工作约定是版本文档；USER/MEMORY/GLOBAL是同一逻辑事实的不同视图，不建立独立事实副本。初始上下文预算取模型窗口25%、最多12000 token，其中SOUL/身份/约定最多2000，USER/GLOBAL最多2000，相关记忆/来源最多4000，任务/成果最多4000；不足窗口按当前请求、权限/纠正、任务、相关事实排序缩减。超预算必要边界先压缩/按需读取，不能静默截掉；这些数值为可调工程基线，非Muse参数。

一期iCloud允许后接，先用认证Mac通道同步同一协议，两端保有本地状态；后续iCloud增加传输适配器，不重新设计画像。彻底遗忘和受控备份具体方案见[POLICIES](POLICIES.md)。

任务执行另用 `execution-task` 与 `task-checkpoint` 两种同步记录，与 `ActivityRecord` 的展示进度分开。当前 Core 已支持本地 epoch 比较交换、同事务检查点提交、已确认交接和失联分支；它尚未连接到 Pi/聊天步骤，也不提供离线设备间的全局互斥。具体边界见 [RUNTIME_PROTOCOL](RUNTIME_PROTOCOL.md)。

## 2026-10-10 外部只读来源记录

新增 `ReferenceDocumentRecord`，保存用户确认导入的 Notion 页面、明确选择的 Obsidian Markdown、或 QQ 邮件摘要的内容、provider/external ID、来源 ID、导入 ID、摘要哈希和更新时间。导入会在一个事务中写 `SourceRecord`、`ImportRecord` 与文档修订；相同内容重复导入不增加记录，更新保留修订。彻底删除写 tombstone 并清除三类当前记录和历史。连接器内容按用户当前请求进行有限关键词匹配，编码为不可信 JSON，仅进入相关模型上下文，不进入 USER.md 事实记忆。

## 2026-10-11 端侧 Agent 工作区迁移

手机 Agent 的会话工作区仍是本机隔离的中间材料，不进入 SQLite 长期记忆，也不会自动同步到 Mac。用户在资料迁移中选择“包含聊天记录、活动、AI 迁移原文和任务草稿”时，归档会只导出归档中存在的会话草稿；不含聊天的迁移包排除草稿。ZIP v2 使用 `agent-workspaces.jsonl`，原有 ZIP v1 与 JSON 迁移包继续读取。导入前检查会话归属、相对路径、文件数、单文件/总容量和 SHA-256；同内容跳过，同路径不同内容保留本机版本，并把导入草稿另存到 `_openmuse_import_conflicts/`。

资料库记录与文件系统不能构成同一个 SQLite 事务。若资料记录已导入、草稿恢复因本机存储故障中断，App 会说明部分完成；用户修复存储后重复导入可补回草稿而不重复写入记录。这个功能解决显式迁移，不替代自动双端同步、iCloud、长期记忆或正式构件保存。

2026-10-11 证据校验补充：每条新回顾提案必须为每个来源用户消息提供一段逐字引文，解析器按 UTF-8 字节核对引文确实存在于对应消息；缺引文、错来源、助手来源和伪造片段都会丢弃。身份页同时展示引文和完整来源。用户采纳前再次核验来源是否仍匹配；来源已变化时建议转为过期且不写入。旧提案仍可解码，历史提案缺少 evidence 字段时保留旧来源展示路径。逐字匹配只证明引文存在，不能证明模型的归纳在语义上成立，也不能校准模型自评把握度，所以仍需用户逐条审阅。

2026-10-11 记忆更新补充：Dreaming 对比现有记忆时，模型只收到近期用户表达相关的 active、user scope、非推断、非敏感且仍有效 claim；解析器复用同一筛选结果，不能针对未提供给模型的其他记忆生成更新。更新提案同时保存目标 claim 的 `updatedAt` 快照、逐字引文和每条来源用户消息全文的 SHA-256 摘要。用户确认后，SQLite 事务保留旧 claim 的新修订、以 `superseded` 状态指向新 claim、设置旧有效期结束、新 claim 保存来源/证据/生效时间，并更新提案状态；USER.md 自动维护区重建为当前有效视图。接受的模型改写仍标为推断。目标 claim 改变或来源消息正文被编辑时提案过期；全文摘要校验会发现引用句仍留在已修改正文中的情况。该路径仅覆盖模型找到的单条相关记忆，不是通用冲突检测，也没有取代明确纠正句式的现有规则；拒绝即无修改，采纳后的纠正仍需由用户再次编辑。

## 2026-10-12 USER、MEMORY、GLOBAL 三种记忆视图落地

SQLite 中的 `MemoryClaimRecord` 是记忆的唯一结构化真值。`USER.md` 只展示当前画像类别的有效 claim；`MEMORY.md` 展示所有当前有效 claim，并补充类别、日期、来源类型、范围、可信度与有效期；`GLOBAL.md` 按主题生成通往 `MEMORY.md` 的短索引。三个文件的自动维护条目都带同一 claim ID，不能各自形成相互竞争的事实副本。被替代、撤销、尚未生效或过期的 claim 不进入当前视图；旧版本留在结构化修订记录中。

聊天或记忆列表的更新先持久化结构化 claim/来源，再用一个 SQLite 事务更新三份 Markdown 文档修订及同步事件；事务中断时，SQLite 里的 claim 仍是准，重开工作区会重建文件视图。从 `USER.md` 或 `MEMORY.md` 编辑自动维护条目时，claim、来源和三份文档修订放在同一 SQLite 事务中提交。`GLOBAL.md` 的自动索引不可通过改链接来改事实；用户的手写内容放在自动维护区之外并保留，且不自动升级为结构化事实。首次创建的模板会说明这些区域的边界。彻底忘记一条 claim 时，三份视图都重建并清理对应文档历史；文件副本写入中断时，重开工作区会从 SQLite 修复。

`appendExplicitMemory` 也改为创建带来源记录的结构化 claim，不再只向 `USER.md` 追加一条游离文本。旧版 `USER.md` 中的自动维护标记会在首次重建时迁移到新的自动区域；已有手写正文会保留。

`SOUL.md` 仍按独立人格修订处理：修改保留来源、会告知用户并可撤销；`HEARTBEAT.md` 仍呈现结构化计划，编辑由计划记录流程处理。它们不会被误当成用户事实，也不会进入 USER/MEMORY/GLOBAL 三视图。

与 Muse 的关系：这些责任划分是 OpenMuse 的本地可迁移实现方案，不是对 Muse 未公开文件 schema 或 dreaming 算法的复刻声明。公开资料能确认文件可编辑和记忆会跨聊天使用，但没有披露官方文件与数据库的具体读写映射。此实现也不等于已完成 Muse 式通用自动抽取、主动 dreaming 或通用事实冲突判定。
