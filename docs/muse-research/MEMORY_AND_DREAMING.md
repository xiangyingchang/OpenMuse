# 记忆维护与 dreaming 研究笔记

日期：2026-10-10。来源为社区归档固定版本；尚非官方实现证明。主来源：[self_improvement.md](https://github.com/win4r/MuseAI-Skills/blob/38bbb45a2c5a0f70de975f6387385770b9ad8aac/home/hatch/docs/self_improvement.md)。以下为原创归纳，不转载原文。

## 快照描述了什么

| 维护工作 | 归档描述的节奏与产物 |
|---|---|
| 记忆整理 | 有新信息时按小时合并至 MEMORY.md；新陈述替代旧陈述，日期笔记保留变化轨迹；会话中也应及时记录 |
| 关系维护 | 按小时维护人物/群体页，整理事实、关系历史和亲近程度 |
| 点子筛选 | 每日结合实际背景生成点子，按可行性、适合程度和新颖性排序 |
| 目标研究 | 夜间每日研究目标相关资料，形成简报、下一步，有时识别隐含目标 |
| Dreaming | 每晚回顾近期交流的有效之处、关系裂痕与用户变化；输出日期反思、修复线索和行为总结 |
| 技能复核 | 每日检查重复工作与现有技能，保留有效变化、淘汰无益变化 |
| 安静时刻整理 | 一段充分交流结束后做有限整理，每日次数受限 |

归档还要求以记录的理由和证据解释建议，追踪排队、尝试、交接与交付；执行成功不能单独证明用户收到结果。以上是文档声明，未实测周期、产物或交付链路。

## 我们的研究解释

Dreaming 更接近“回顾如何更好地与这个人相处”，记忆整理更接近“更新知道的事情”。例如用户纠正旅行方案太赶：事实层保存本次节奏约束；反思层检查自己是否过早排满行程；行为层下次先给松紧两档选择。这是 OpenMuse 的合成演示，不是 Muse 的真实运行记录。

因此建议研究三种不同产物：可证实的事实更新、仍待验证的理解、可观察的协作调整。不要把反思直接当新事实，也不要把生成一段人格文字当作帮助已经改善。评估应看下一次类似情境的实际回应是否更合适。

“修复”值得重点核对：指出遗漏、承认理解错误、修正计划，可能比增加提醒更有用。但没有证据不能假定 Muse 会主动道歉、发消息或自动修改 SOUL。反思如何汇入 SOUL/USER/GLOBAL、何时告诉用户，是待验证的连接。

## 对 OpenMuse 候选设计的影响

- 会话中的重要信息及时持久化，不能等后台 dreaming 才记住。
- 增加维护运行记录：输入来源、所用状态版本、候选变化、实际提交、未采用原因、后续验证与交付状态。
- 把事实维护、关系页、点子、目标研究、协作反思、技能改进作为不同任务类型，分别控制预算和通知。
- Dreaming 输出首先是带来源的反思候选；事实变更走记忆事务，人格变更走差异/告知流程，工具权限不随之变化。
- “夜间”属于 Muse 云端环境的材料描述。手机端采用实际可执行机会、漏跑状态和有限补跑，不承诺锁屏准时完成。
- 同一输入窗口与维护类型有稳定运行标识，避免同步或重试重复写入。新增用户纠正与遗忘时重新校验候选，不能提交过期反思。

这些是研究后的设计建议，尚未实施。与 [核心存储方案](../MEMORY_STORAGE.md) 一同讨论，不声称复刻闭源算法。

## 当前尚不清楚

实际运行能否跳过、如何选择近期窗口、矛盾如何解决、反思能改哪些文件、SOUL 修改是否固定通知、修复何时对外表达、用户暂停后是否停止相关维护，以及遗忘是否覆盖 dreams 和旧修订。按 [场景清单](SCENARIOS.md) 随迭代核对，避免一次向用户索取所有资料。
